## Архитектурные компоненты

| Компонент | Назначение | Взаимодействие |
| --- | --- | --- |
| Браузер | Просмотр каталога пользователем | Отправляет запрос к странице GitHub |
| Веб-интерфейс GitHub и обработка Markdown | Преобразование документа в читаемую страницу | Читает Markdown и показывает его браузеру |
| Git-репозиторий | Хранение файлов и истории изменений | Предоставляет GitHub нужную версию документа |

Это прототип каталога на основе документации. Отдельное приложение и база данных для него не нужны. Данные описаны в таблице service-models.md и в разделах service-examples.md.

## Использованные элементы Markdown

| Элемент | Применение |
| --- | --- |
| Заголовки #, ##, ### | Название и разделы README |
| Маркированные списки | Структура данных, технологии и источники |
| Нумерованные списки | Компоненты и шаги просмотра |
| Таблицы | Категории моделей и структура репозитория |
| Ссылки | Документы проекта, PR и источники |
| Жирное выделение | Автор, группа и названия технологий |
| Кодовый блок | Команды git clone и cd |
| Встроенный код | Названия файлов и каталогов |

## Порядок просмотра

Для просмотра на GitHub нужны браузер и Интернет. Нужно открыть репозиторий, прочитать README и перейти по ссылкам на таблицу моделей и примеры сервисов. Для локального просмотра нужны Git и редактор с поддержкой Markdown: сначала выполняются git clone и cd gfss, затем открывается README.md и его предпросмотр. Установка Python, Docker и пакетов для этого прототипа не требуется.

## Проверка

README разобран локально как GitHub Flavored Markdown через Pandoc. Проверено наличие восьми типов разметки: заголовки, два вида списков, таблицы, ссылки, выделение, блок команд и встроенный код. Кодовый блок закрыт. В тексте используются обычные дефисы.

Разметка проверена локально; визуальная проверка отображения README непосредственно на GitHub пока не выполнена. Её нужно завершить отдельно: открыть README в режиме отображения и проверить заголовки, обе таблицы, ссылки и блок команд.

## Ответы на контрольные вопросы

1. README нужен, чтобы посетитель сразу понял назначение проекта, структуру файлов и порядок начала работы.
2. Документацию структурируют заголовки, списки, таблицы, ссылки, выделение и блоки кода.
3. В инструкции нужны предварительные условия, зависимости, точные команды в правильном порядке и ожидаемый результат.
4. Реальные секреты нельзя публиковать, потому что посторонние могут получить доступ к аккаунтам и сервисам. Удалённый секрет также может остаться в истории Git.
5. Хорошая документация помогает новому участнику быстрее разобраться в проекте, повторить запуск и вносить изменения без лишних вопросов.
